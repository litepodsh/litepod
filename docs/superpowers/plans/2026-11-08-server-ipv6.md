# Compatibilidad IPv6 en servidores: plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Conectar servidores por IPv6, que el instalador detecte y muestre IPv4 e IPv6, y que los dominios publiquen A y AAAA.

**Architecture:** `LITEPOD_PUBLIC_IP` sigue siendo IPv4 y obligatoria, porque alimenta `sslip.io`, CORS y DNS. IPv6 se agrega como dato opcional aparte: `LITEPOD_PUBLIC_IPV6` para el host local y `servers.public_address_v6` para servidores remotos. La salida IPv6 de la API usa una red nueva, `litepod-egress6`, y `litepod-network` no se recrea, así que las apps no se interrumpen.

**Tech Stack:** Rust/axum/sqlx (SQLite), SvelteKit + Svelte 5, shadcn-svelte, bash, Podman rootless (pasta).

**Spec:** el pedido del dueño del 2026-11-08 (no hay documento aparte).

## Límites conocidos (fuera de este plan)

- **Hosts solo IPv6:** `ghcr.io` y `github.com` no publican AAAA (verificado con `dig`, 2026-11-08). Sin NAT64 no funcionan las imágenes de ghcr, incluida `railpack-frontend`, ni los despliegues desde GitHub. El instalador sigue exigiendo IPv4.
- Las apps en `litepod-network` siguen solo con IPv4 de salida. El tráfico IPv6 de entrada llega por Caddy.
- `dns_validation::evaluate` da válido si *una* dirección coincide: un AAAA viejo junto a un A correcto pasa la validación.

4. Respuesta basura del servicio de detección (HTML): se descarta y no llega al `.env` (Task 2).
5. Reinstalación con un valor manual en `.env`: no se sobrescribe (Task 2).

## Decisión de UI

Sin dropdown para elegir IPv4 o IPv6:

- **Host SSH:** la dirección escrita ya determina el protocolo.
- **Dirección pública:** un servidor con ambas debe publicar A y AAAA. Elegir una dejaría sin acceso a los clientes de la otra.
- **sslip.io:** es el único caso con un solo valor, y se resuelve con la regla de la Task 4.
